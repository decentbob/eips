# EIP-0051: Graduated Storage-Rent Grace Period for Token Boxes

* Author: bob
* Status: Draft
* Created: 25-Sep-2026
* License: CC0
* Forking: Soft-fork needed

## Abstract

An underfunded box holding tokens or registers is today swept whole the moment it
reaches storage-rent age. This EIP adds a grace window of 20,000 blocks (about 28
days). During the window the box cannot be swept, only refreshed: script and
registers kept, the rent paid, and the refresher paid with a share of each fungible
token. The share starts at 2^-32 and doubles every 625 blocks, reaching 1/2 in the
last stage; after the window, normal collection applies. Refreshers act as soon as
the share covers their cost, so the box pays its rent in its own tokens and the
protocol never needs a token price.

## Motivation

Storage rent has a cliff. A box that can pay its fee loses only the fee; a box a
few cents short loses everything, including tokens, NFTs and registers.

Such boxes are common. Wallets spend only the inputs a transaction needs, so old
token boxes sit untouched in active addresses, and token boxes are usually created
near the minimum value, far below one rent.

The EIP keeps the purposes of storage rent: state control, miner revenue and
app-neutrality. An underfunded box still pays a full rent, and slightly more,
but does not lose everything. Third parties can also rescue boxes they care about.

## Specification

### Current rule

`ErgoInterpreter.verify` takes the storage-rent path for input B when
`HEIGHT - B.creationHeight >= StoragePeriod` (1,051,200), the proof is empty and
context variable 127 holds a `Short` output index. With
`storageFee(B) = storageFeeFactor * size(B)` (factor 1,250,000 nanoERG/byte):

* if `B.value <= storageFee(B)`, the spend is valid whatever the outputs;
* otherwise output O at the index must keep every register except R0 and R3, have
  `creationHeight == HEIGHT` and hold at least `B.value - storageFee(B)`.

A `false` result invalidates the input. Only an exception (bad variable type, index
out of range) falls back to the box's script. This EIP keeps that behaviour and uses
`storageFee` as computed in 64 bits by EIP-48; today's 32-bit product wraps for boxes
of 1,718 bytes or more.

### Scope

B is in scope when it is spent through the storage-rent path and:

1. `B.value <= storageFee(B)`;
2. B holds at least one token or at least one register R4–R9; and
3. B holds no EIP-27 re-emission token. EIP-27 forbids outputs carrying that token,
   so such a box could never be refreshed; EIP-48 covers these boxes.

Everything else follows existing rules.

### Window and stage

Constants: `N = 32`, `D = 625` (about 21 hours), `W = N * D = 20,000` (about 28
days), `L = 720`. Let `T = B.creationHeight + StoragePeriod` and `t = HEIGHT - T`.

* `t >= W`: the window is over; existing rules apply.
* `t < W`: stage `k = t / D` (integer division), `0 <= k < N`; share `2^(k-N)`.

### Refresh rule

While `t < W`, the storage-rent spend of an in-scope B is valid only if output O at
the index in variable 127 satisfies:

1. `O.propositionBytes == B.propositionBytes`;
2. O.R4–R9 equal B.R4–R9;
3. for every token id in B (amounts summed per id), O holds at least
   `retained(a, k) = a - (a >> (N - k))`;
4. `O.creationHeight == HEIGHT`.

and the transaction satisfies:

5. **Unique refresh outputs.** No two inputs spent through the storage-rent path
   whose rule requires a refresh output (funded boxes, and in-scope boxes during
   the window) name the same output index.
6. **Rent paid.** Outputs whose ergoTree equals the rent tree R (below) and whose
   `creationHeight == HEIGHT` hold in total at least the sum of `storageFee(B)`
   over all in-scope inputs.

Taken tokens and B's ERG may go to any output. The haircut is one right shift of at
most 32 bits; amounts below `2^(N-k)` are not reduced, so NFTs and other amount-1
tokens are never haircut and can only be saved by a sponsored refresh.

Conditions 5 and 6 are evaluated once per transaction. Cost: `StorageContractCost`
plus `tokenAccessCost` per token of B and O, per in-scope input.

### Rent tree R

R is the standard miner-fee proposition (`ErgoTreePredef.feeProposition(720)`) with
one added conjunct, `HEIGHT >= SELF.creationHeight + L`. A rent box can therefore be
claimed only by the miner of a block at least L blocks after the refresh. The exact
tree bytes are fixed by the reference implementation.

### Activation

Soft-fork vote as for 6.0: more than 90% of blocks over 32 voting epochs of 1,024
blocks, then 32 epochs until activation, which raises the block version from 4 to 5.
The rules apply to every storage-rent spend in blocks of version 5 or higher. Boxes
already inside their window at activation are protected from their current stage.
EIP-48 is gated on the same version, so both can activate in one vote. This EIP
requires EIP-48 or an equivalent 64-bit fee.

### Soft-fork argument

Every spend allowed here is valid today: an underfunded box passes the current
check for any outputs, and rent boxes are ordinary outputs. The EIP only
invalidates full sweeps of in-scope boxes during the window and storage-rent spends
that share a refresh output. Old nodes accept blocks built under the new rules.

## Rationale

**Where the rent goes.** The rent goes to miners, but not to the miner who includes
the refresh. Refreshers compete on the token share, so any cost a refresher gets
back is competed away. If the including miner received the rent, a pool could
refresh, collect the rent in the same block and bid the share down to the
transaction fee. The owner would then pay almost nothing, and holding tokens in
underfunded boxes would become the cheapest option. R pays a later miner instead:
a refresher with hash share s gets back about s of the rent on average, not all of
it.

Pay-to-reemission would suit, but miners spending re-emission tokens must already
pay exactly that amount into it. Those payments would satisfy condition 6 with no
rent paid, and separating them would need a change to EIP-27.

**Why no deposit.** A rent deposit in O would roughly double the refresher's cost,
delay refreshes and stop boxes worth under about two rents from being rescued, all
without better rent collection. Without it, a refreshed box pays in tokens again
at its next expiry. The owner can add ERG at any time.

**Why doubling.** Doubling is scale-invariant: each step raises the share by the
same ratio, so the auction is equally precise for small and large boxes. A refresher
acts at the first profitable stage, so the take is at most about twice the refresh
cost. The only unbounded loss is the stage-0 floor, value × 2^-32. It exceeds the
refresh cost only for boxes worth more than about 4 × 10^9 times that cost.

**Why constants.** About a month gives owners time to notice and refreshers a fine
auction, and there is no clear reason to tune it by vote. Constants also keep each
box's schedule fixed and add no new parameter. A new parameter would need node
fixes first: v6.0.6 rejects parameters it does not know (ergo PR #2422, open).

### Worked example

C is the refresher's cost: rent + transaction fee + O's minimum value, minus
B.value. For a typical single-token P2PK box of about 112 bytes, C is close to the
rent itself, about 0.14 ERG.

| Fungible token value | Stage | Day | Taken |
|---|---|---|---|
| 10^7 C | 9 | 8 | 1.19 C |
| 10^4 C | 19 | 16 | 1.22 C |
| 100 C | 26 | 23 | 1.56 C |
| 10 C | 29 | 25 | 1.25 C |
| < 2 C | none | 28 | collected as today |

The owner pays between one and about two rents.

### Alternatives

| Proposal | Owner outcome | Drawback |
|---|---|---|
| Status quo | Loses all contents | Loss unrelated to the amount owed |
| Burn tokens (EIP-33) | Loses all contents | Destroys value; owner no better off |
| Miner-only collection (relay policy) | Loses all contents | Changes who collects, not the loss |
| Grace window, sponsored refresh only | Saved only if someone pays | No incentive to rescue |
| Token auction to miners | Loses all contents | Needs bidding and a proceeds contract |
| This EIP | Pays one to two rents, in tokens | New refresh conditions |

## Security and economic considerations

* **Delayed refreshes.** A refresher may wait for a larger share but risks being
  pre-empted. The owner keeps at least half until the window closes.
* **Contract boxes.** Removing tokens may break a contract's invariants, though
  that is still better than a full sweep. Contracts that need their tokens should
  refresh themselves.
* **State growth.** Refreshed boxes have paid rent. Worthless boxes are collected
  at most W blocks later than today. Rent boxes are claimed after L blocks.
* **Top-up griefing.** Preventing collection requires paying the rent, which is
  the intended outcome.

## Companion measures (non-consensus)

* Wallets and SDKs: create token boxes with at least one rent of ERG, and warn about
  boxes approaching expiry.
* Mining software should claim matured rent boxes, as it does fee boxes.
* If nodes stop relaying storage-rent spends so that only block producers collect,
  refreshes should stay relayable. Otherwise competition weakens and owners pay a
  higher share.

## Open questions

* Whether R should instead be the EIP-45 redistribution box, if adopted. That box can
  be spent once per block, so rent would need a deposit contract that can only
  be merged into it.
